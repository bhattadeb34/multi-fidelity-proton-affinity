# Reproducibility and configuration

This repository separates scientific choices, derived values, and archived
execution records. That distinction matters when reproducing the paper or
starting a new screening campaign.

## Scientific choices

The production screening settings are in
`screening/config/pipeline_config.json`. They include the PA window, Morgan
fingerprint definition, consensus-feature rule, RandomForest settings, LLM
request settings, and Pareto objectives. The defaults reproduce the reported
workflow. A changed value defines a new run and requires regeneration from the
earliest affected stage, as listed in `screening/config/README.txt`.

The model-comparison scripts expose the fold count, random seed, variance
threshold, redundancy-correlation threshold, and target-correlation pool size
as command-line arguments. The reported settings are also written into each
`cv_results.json` file.

## Values derived from data

Consensus features are reconstructed from `cv_results.json`. They are not
copied into screening scripts. The training PA limit and correction statistics
used by the screening rule check are calculated from the corrected k-means
target table. The loader rejects the stale target table that broadcast one DFT
value across every site of a multi-site molecule.

Candidate counts, model names, selected features, lead labels, and plotting
statistics are read from saved artifacts. Plotting scripts do not replace
calculated values with manuscript numbers.

The PubChem and ZINC checks for the provisional five leads are independently
reproducible with
`data/screening/database_validation/top5_20260816/retrieve_top5_records.py`. The
archived raw responses retain the original request URLs, retrieval times,
status codes, and response hashes because public database records can change.

## Selection decisions

No molecule identifier is inserted directly into the retrieval, prediction,
LLM, or Pareto-selection code. Pareto candidates are produced from the
configured objectives. The final five leads are generated by
`12_select_dft_leads.py` from the DFT PA window, the same-ring donor/acceptor
motif, and the archived functional-group review in `stability_review.csv`.
That review is the one human judgement step and is kept as an explicit input
rather than hidden in code.

## Validation boundaries

- NIST uses five-fold shuffled CV with one row per molecule.
- k-means uses `GroupKFold` so every protonation site from one molecule stays
  in the same outer fold.
- Imputation, filtering, scaling, and Lasso selection are fitted only on each
  outer training fold.
- DFT-augmented site rows require exact neutral and protonated SMILES matches.
- Fixed seeds control the stochastic estimators and conformer generation.
- Exact fold identity can depend on the recorded scikit-learn version when
  groups have equal sizes. The environment is recorded in
  `docs/clean_env_versions.json`.
- Hosted language-model output is not expected to be bitwise reproducible.
  The paper run is therefore represented by its raw responses, model
  identifier, prompt, retry records, token counts, and checksums.

## Credentials and machine paths

Credentials are never read from repository files. Stage 6 accepts an explicit
Vertex service-account path or standard Google application-default
credentials. Reusable scripts resolve data and output paths from the repository
root. Machine-specific paths that appear in archived SLURM output or the exact
submission script are retained only as historical execution provenance.
